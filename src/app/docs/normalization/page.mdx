# Normalization & quality

Before Gemini spends tokens, Remotify forces jobs into a **canonical shape** and drops low-signal titles. Owners: `src/normalizers/index.js`, `src/utils/job-quality.js`, `src/scrapers/schema.js`.

## Why this layer exists

Scrapers disagree on everything: “Sr. React Eng”, “Senior React Engineer”, “Remote - US”, skill tags as strings vs arrays. Without normalization:

- Dedupe misses duplicates → wasted AI  
- Profile matching becomes noisy  
- Apply ATS detection still works on URL, but human digests look chaotic  

## Zod boundary (ingress contract)

`JobSchema` in `scrapers/schema.js` is the fence. Invalid jobs never enter normalize/AI.

Minimum expectations typically include: title, company, description, apply URL, source. Scrapers may soft-drop locally before returning.

## Normalization behaviors

### Titles

Map noisy variants into stable buckets used for allow/block and display consistency (seniority + role family where possible). Exact maps live in the normalizer — extend there, not in scrapers.

### Skills

1. Merge scraper-provided skills + tokens extracted from description/title.  
2. Apply `SKILL_MAP` aliases (`nodejs` → `Node.js`, `postgres` → `PostgreSQL`, …).  
3. Case-insensitive dedupe.  
4. Persist as `skills[]` on the Job.

### Location / remote

Detect Worldwide / USA / UK / EU remote signals when present. Empty remote signal often becomes a safe default such as **Worldwide Remote** so downstream filters have something to read. `isRemote` stays true for this product’s thesis.

## Deduplication (immediately after normalize)

Owner: `utils/deduplicate.js` (+ `similarity.js`).

| Pass | Key | Intent |
| --- | --- | --- |
| 1 | Normalized apply URL | Same posting, many mirrors |
| 2 | company + title | Same role, tracking params differ |
| 3 | Jaccard / similarity vs recent DB | Near-duplicates across sources |

## Quality prefilter

Owner: `utils/job-quality.js`.

| Check | Effect |
| --- | --- |
| Title blocklist | Drop recruiters spam / unrelated roles |
| Title allow orientation | Prefer engineering-shaped titles for this candidate |
| Remote sanity | Drop obvious onsite-only noise when detectable |
| ATS ranking | Prefer Greenhouse/Lever/Ashby URLs when budgeting AI slots |

**Product rule:** it is better to score 12 great auto-ATS jobs than 40 mediocre aggregates under Hobby cron limits.

## BDD-style scenarios (product rules)

### High-fit auto-ATS is preferred

**Given** two jobs with similar scores  
**And** one is Greenhouse and one is a generic board  
**When** AI budget is tight  
**Then** quality ranking should prefer the Greenhouse URL for scoring/enqueue  

### Notify vs apply thresholds differ

**Given** `min_match_score=85` and `apply_min_score=75`  
**When** a job scores 80  
**Then** it may enqueue (if ATS/quota allow) but should not enter the top Telegram interrupt list  

### Scrapers never invent apply URLs

**Given** a parser failure  
**When** the scraper cannot find a real apply link  
**Then** it returns no job (or invalid rows die at Zod) — never a homepage guess  

### Tailor does not invent employment

**Given** locked master resume JSON  
**When** resume tailor runs  
**Then** it may reorder/emphasize — not fabricate employers or degrees  

## How to extend safely

1. New skill alias → `SKILL_MAP` only.  
2. New junk title pattern → quality blocklist.  
3. New source quirks → fix in that scraper, then rely on shared normalize.  
4. Add a BDD scenario here when product behavior changes.
